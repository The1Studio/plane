# Fork-views-ext SQL/ORM analysis

**Coverage**: 5 dirs read — `apps/api/plane/views_ext`, `apps/api/plane/cascade_ext`, `apps/api/plane/project_ext`, `apps/api/plane/workspace_ext`, `apps/api/plane/issue_defaults_ext`. ORM sites reviewed: ~80 grep hits across `.objects.`, `select_related`, `prefetch_related`, `connection.cursor`, `.raw(`, `.count()`, `.exists()`, `.aggregate()`, `values_list`, `bulk_create`, `bulk_update`. No `.raw(` / `connection.cursor` / `.aggregate()` / `len(qs)` instances found in production code. All five target apps are fork-owned — every finding below is fork-safe: yes.

## Top findings

1. **views_ext/views.py:172-174 — global `Prefetch(... .objects.all())`** (3 lines). The single biggest waste in the surveyed code: each grouped issue page does THREE full-table scans of `IssueAssignee` / `IssueLabel` / `ModuleIssue` regardless of how many issues are in the page or how the workspace is scoped. Cost is O(total tenant rows), not O(page size). Fix: scope the prefetch querysets to the outer issue ids (or to `OuterRef("id")`). Highest-impact change with a one-line patch per row.
2. **cascade_ext/service.py:106 + 432 + 555 — parent-chain N+1 inside `apply_cascade`/`apply_module_cascade` rejection loops.** A single rejected id can issue up to 20 SELECTs to walk ancestors; a rejected batch of M ids can issue up to 20×M. Fix with one recursive CTE (or a single bulk-fetch followed by in-Python chain walk) — eliminates the per-id amplification and replaces it with O(1) round-trips regardless of M.
3. **views_ext/views.py:507-510 — redundant nested `Issue.issue_objects.filter(id__in=Issue.issue_objects.filter(...))` subquery** that duplicates `workspace__slug=slug` and materializes an intermediate id set before the outer JOIN re-applies it. Collapsing the inner Q into the outer filter removes one full pass over `issues` and the planner can pick a single index.
4. **cascade_ext/service.py:461 and 584 — `list(Issue.issue_objects.filter(id__in=...))` for cascade-write paths** loads every Issue column just to update `state_id` and `updated_at`. `.only("id","state_id","updated_at")` cuts the read payload by an order of magnitude on wide Issue rows.
5. **project_ext/service.py:112, 118, 234 — full-row Project fetches for id-gather / update paths.** Each call pulls every Project column when only `.id` (or no row at all for the `.update()`) is consumed. Replace with `.values_list("id", flat=True)` and split the existence check from the bulk update so the two queries stop sharing an unindexed scan.
