Coverage: read `apps/api/plane/app/views/analytic` (3 files: `advance.py`, `base.py`, `project_analytics.py`), `apps/api/plane/app/views/module` (3 files: `base.py`, `archive.py`, `issue.py`), and `apps/api/plane/app/views/notification` (1 file: `base.py`) — 7 files, ~143 ORM-site grep hits reviewed (`.objects.`, `.raw(`, `connection.cursor`, `select_related`, `prefetch_related`). Zero hits for `.raw(` or `connection.cursor`. All cited files live under upstream core (`plane/app/views/...`) — every row is fork-safe: no unless explicitly marked.

## Top findings

1. **module/issue.py:50-81 — list endpoint fires 4 subqueries per Issue.** Largest table in scope; this is the hottest path on every module view. Collapsing into conditional aggregates or LEFT JOIN + GROUP BY is the single biggest win.
2. **module/base.py:78-296 + module/archive.py:41-247 — 12-subquery annotation per Module, duplicated across two viewsets.** Same shape, twice. Extract a shared helper and collapse the state counts and estimate sums into a single aggregate per row.
3. **notification/base.py:282-287 — `MarkAllReadNotificationViewSet` materializes every unread notification into Python just to set `read_at`.** Replace the SELECT + bulk_update with a single `notifications.update(read_at=...)`.
4. **analytic/advance.py:83-105 + analytic/advance.py:187-196 — `get_overview_data`, `get_work_items_stats`, and `project_chart` together issue up to 17 separate COUNT queries per analytics page load.** All replaceable with a handful of `aggregate()` calls (and many of the 7 in `project_chart` are not even chart-rendered).
5. **analytic/project_analytics.py:64-71, 122-128, 193-207, 336-342 — repeated `CycleIssue/ModuleIssue.values_list("issue_id")` then `id__in=...`.** Eight occurrences of materializing issue ids in Python and re-evaluating as a giant IN clause; drop the values_list and keep the join in SQL.
