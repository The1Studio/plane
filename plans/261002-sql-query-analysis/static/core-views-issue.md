## Top findings

1. **relation.py:174 - ~11 heavy duplicate queries per `list` request.** The response dict evaluates the same ArrayAgg+Subquery-annotated issue queryset once per relation bucket, each re-scanning the issue's relation rows. Single-fetch + Python partitioning turns ~11 heavy queries into 2 light ones. Highest per-request cost in scope.
2. **base.py:160 - N+1 on the main issue list's fields/expand path.** The select_related/prefetch at base.py:105 is attached to `issue_queryset`, but the serializer receives the bare `queryset` - per-row queries for every expanded relation, multiplied by page size on the hottest endpoint.
3. **activity.py:36 / activity.py:48 - unbounded history load.** All IssueActivity + IssueComment rows for an issue are fetched and merged in memory (activity.py:81) with no pagination; grows without bound on long-lived issues.
4. **base.py:770 - `len(issues)` counts by materializing full Issue rows.** A `COUNT(*)` away from being free; the endpoint is bulk delete, so the scan can be large.
5. **archive.py:334 - per-row `IssueSerializer` inside the bulk-archive loop.** Serialization cost scales linearly with the bulk request instead of one batched pass.
