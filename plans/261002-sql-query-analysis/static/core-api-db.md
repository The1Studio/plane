## Top findings

1. **`IssueSerializer.to_representation` N+1 (serializers/issue.py:321-341)** - every issue row serialized on list endpoints (views/issue.py:401, views/cycle.py:892, views/module.py:638,848) triggers 1-4 fresh queries for assignees/labels; a 20-row page costs 40-80 extra queries. Prefetch and serve from cache.
2. **`IssueExpandSerializer` per-row relation queries (serializers/issue.py:858,864)** - intake list serializes nested issues (views/intake.py:116) whose queryset (views/intake.py:74-83) prefetches neither `label_issue` nor `issue_assignee`: 2+ queries per intake row.
3. **exists()-then-fetch double lookups (views/cycle.py:313, views/issue.py:444,1425, views/module.py:207, views/state.py:92)** - the external-id conflict path runs the same predicate twice; collapse to one `.first()` and combine with a partial unique index on `(project_id, external_source, external_id)` (columns unindexed today, db/models/issue.py:161-162).
4. **Redundant post-save refetches (views/cycle.py:345,550, views/module.py:238, views/issue.py:467,1449,1616,919,1052,1166)** - `serializer.instance` already holds the saved row; each of these adds a pointless SELECT on hot create/update endpoints.
5. **Migration N+1 loops (db/migrations/0053:33, 0067:29-53, 0077:68-89)** - per-row lookups inside full-table backfills; one-shot but O(rows) round trips that can turn `migrate` into hours. Hoist lookups into dicts/prefetch before the loop.
